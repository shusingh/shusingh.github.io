The [AI trip planner](/projects/trip-planner) worked fine. Type a destination, pick some dates, get an itinerary back. What it didn't do was look like a product, and it definitely didn't feel like a map tool, which is strange for an app whose entire value is "where are these places relative to each other." The map, when there was one, showed up after the fact, on a separate results screen, as an afterthought to a list.

The redesign, which I've been calling Atlas, had two real goals: put the map at the center of the experience instead of the edge of it, and stop depending on a component library that fights me every time I touch it.

## Retiring HeroUI for a system I actually own

HeroUI had been fine until it wasn't. Every few months a version bump would quietly demand a Tailwind major version I wasn't ready for, and the last one wanted Tailwind v4 while the rest of the app's tooling was still v3-shaped. Chasing a UI kit's opinion about my build chain is not a fight worth having twice.

So Atlas drops HeroUI entirely in favor of a small local set of primitives in the shadcn tradition: own the component source, keep Tailwind v3, take zero version-drift risk from a dependency that was only ever providing buttons and inputs. The tradeoff is real, I now own maintenance for a chip, a button, a date range field, and an input, but for a project this size that's a few hundred lines, not a liability.

Leaflet made the same case for itself. MapLibre GL JS paired with OpenFreeMap gives vector tiles with no API key, no usage cap, and no third-party account to manage, which matters for a demo project that should keep working with zero maintenance. The one real gotcha: MapLibre's canvas doesn't automatically notice when its container resizes across a client-side route transition, so the map silently stays the old size until you attach a `ResizeObserver` and tell it to recalculate. A known gotcha in the Mapbox GL/MapLibre family, but the kind of thing you only learn by shipping it and watching the canvas clip itself on the results page.

## Three bugs that only a real user finds

I ran the new build through a scripted browser walkthrough against the live backend before calling it done, zero console errors, all green. Then the actual user (who also happens to be the only stakeholder) tried it and found three things automated testing had no chance of catching, because they were about how it *looked*, not whether it *ran*.

The most interesting one: the date range picker rendered a selected day as solid navy with white text, until the mouse rested on it, at which point the digit vanished. Selecting a range produced a half-and-half color split at the boundary cell. Both looked like theming bugs, and both were actually a single root cause: `react-day-picker` v9 merges your custom `classNames` prop with its defaults per key, meaning if you override `day_button`, you silently strip out the library's own `rdp-day_button` class, the exact class its CSS uses to paint the solid background on selected and range-boundary cells. My override wasn't adding a style, it was deleting one. The fix was to merge with `getDefaultClassNames()` instead of replacing wholesale, and to move the hover affordance from a background tint (which has the same cascade specificity as the selected-day fill, so it can win a tie it shouldn't) to a ring, which never competes with the fill at all.

The other two were smaller but from the same family: vertical centering that used `justify-content: center` instead of `margin: auto`, which looks identical until content overflows and the top half becomes unreachable by scroll; and a generic icon-library compass that, in the reporter's words, "looks like a child drew this." All three shipped clean past an automated walkthrough. None of them would have shipped past an actual person looking at the screen for four seconds. That's the whole argument for testing in a browser instead of trusting a green checkmark.

## Moving off Render, onto Vercel

The backend had been a standalone Go server on Render's free tier, which meant a cold start tax on the first request after any idle period. Moving it to Vercel serverless functions doesn't remove cold starts, but it does mean the frontend and backend can live in the same platform, deploy from the same CLI, and share a account instead of stitching two dashboards together.

Getting there surfaced the best bug of the whole project: Vercel's Go builder does not respect Go's own `internal/` package visibility rule correctly. The moment `api/recommendations.go` imported anything under `internal/`, the build failed with "use of internal package ... not allowed," despite the import being completely legal under a normal `go build`, because both files live under the same module. The builder's synthesized build step resolves the importing file's path in a way that puts it outside the tree `internal/` is supposed to protect. The fix is almost insultingly simple once you know it: rename the directory to `pkg/`. Nothing about the code changes, only the literal string Go's compiler treats as reserved.

The other surprise had nothing to do with code. New Vercel projects ship with SSO deployment protection on by default, which put a login wall in front of both the app and the API, invisible until I actually tried to load the public URL and got redirected to `vercel.com/sso-api`. For a public demo, that protection needed to come off explicitly, project by project.

## What I'd do differently

Ship the browser check earlier and more literally. "Zero console errors" and "looks right" are different claims, and only one of them was actually being tested before the first real look. The CSS custom property bug in particular is worth generalizing: any time a library exposes theming through a prop that merges with its own defaults, assume replace-not-merge until proven otherwise, and check what class or variable you might be deleting rather than only what you're adding.
