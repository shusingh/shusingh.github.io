## System intent

Inference engines like vLLM cache the KV state of recent prompts and reuse it when a new prompt starts the same way. Agents resend the same system prompt and tool definitions every step, and conversations resend their history every turn, so most of a prompt is often already cached somewhere in the pool. A cache-blind load balancer scatters related requests across replicas, and each replica recomputes prefixes another one already holds.

Switchyard is a router that sits in front of a pool of OpenAI-compatible model servers and sends each request to the replica most likely to have its prefix cached, balanced against load.

## Requirements

- Speak the OpenAI API, streaming and non-streaming, and propagate client cancellation to the engine.
- Know what each replica has cached without running a tokenizer on the hot path.
- Add well under a millisecond of latency per request.
- Survive replica failures and restarts without routing to stale beliefs.
- Measure results against named baselines on real hardware, with the method written down before the numbers.

Each request is reduced to a canonical byte form (model, tools, messages) and hashed in fixed-size blocks, each hash covering everything before it, so requests that share a prefix share leading hashes. The router remembers which blocks it sent where, within each replica's KV capacity, with LRU eviction and a TTL.

An optional precise mode goes further: the Go code reproduces vLLM's own `sha256_cbor` block hashes bit for bit, verified against vLLM's functions and against a live engine, and keeps the index in sync from the engines' KV cache events over ZeroMQ.

## Results

Four vLLM replicas of Qwen2.5-1.5B-Instruct on one RTX 4090, agent-session workload, three trials per policy, medians. The cache hit rate is vLLM's own counter.

| Policy | Cache hit rate | TTFT p50 | Requests under 2 s TTFT |
|---|---:|---:|---:|
| round-robin | 32.7% | 3.91 s | 37.0% |
| least-loaded | 31.3% | 6.15 s | 30.8% |
| prefix affinity | 81.7% | 241 ms | 92.6% |

The router adds 104 µs at p50 and 472 µs at p99, measured at 1,000 requests per second on Linux.

## What did not work

I also built `estimated_ttft`, a policy that predicts time to first token for every replica from queued prefill work, uncached tokens, and learned throughput. In my simulator it matched prefix affinity on normal traffic and was far better when one prefix dominated, because it replicates a hot prefix across replicas as load requires.

On the GPU it lost to prefix affinity. The four replicas share one GPU, and the cost model assumed independent compute, so moving a request to an idle replica looked faster when that replica was competing for the same device. I added a shared-accelerator mode to the simulator, which reproduced the GPU result, then tried three device-aware variants of the cost model. None helped, so I reverted them, recorded the attempts in an architecture decision record, and made prefix affinity the default.

## Design decisions

**No tokenizer on the hot path.** Hashing canonical bytes is cheap and model-independent. The router's believed cache hit rate stayed within one point of vLLM's measured rate across every GPU run.

**A simulator that does not share the router's keys.** The simulated engine tokenizes and hashes on its own, so the router's predictions are never perfect by construction.

**Honest benchmarks.** Methodology first, three trials, caches reset between trials, and negative results kept in the report.
